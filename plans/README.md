## Recommended execution order

**No hard dependencies between any of the five** — each touches a different component (005 shares a file with 003, but a different property on the same element) and can be done in any order or in parallel. Suggested order is just by leverage (highest-impact first):

1. **001** — done. Establishes the `key`-remount + `@keyframes` fade-in pattern 002/004 reuse conceptually.
2. **002** — done. Same technique, second-highest severity.
3. **003** — done. Trivial one-line fix.
4. **005** — do this before or after 004, doesn't matter; it builds on 003's `transition-colors duration-150` (which 005 replaces with an equivalent property list plus `transform`), so re-check `Calendar.tsx`'s current class string against 005's file before applying if 003 is ever re-touched.
5. **004** — independent, do whenever.

Plans 001/002/004 add rules to the bottom of `src/app/globals.css` — each uses a distinct `@keyframes` name (`art-fade-in`, `preview-backdrop-in` + `preview-card-in`, `copy-label-fade`), so no collisions if applied in any order. Plan 005 adds **no** CSS — it's a pure Tailwind utility change gated by the built-in `motion-safe:` variant, deliberately not following the custom-`@keyframes` shape of the other three (see its file for why a hover-only scale doesn't need one).
